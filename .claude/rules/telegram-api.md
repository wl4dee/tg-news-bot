# Telegram Bot API — правила проєкту

## Абсолютна заборона: getUpdates

Після `setWebhook` метод `getUpdates` повертає `409 Conflict` **назавжди**, доки
вебхук не знято. Вебхук у цьому проєкті стоїть постійно.

Отже: рядка `getUpdates` у `bot/` не існує. Polling не будуємо ні за яких обставин.
Якщо здається, що потрібен polling — потрібен не polling, а ще один обробник у воркері.

Єдиний легальний спосіб дізнатись `chat_id` — зробити це **до** встановлення вебхука
(пункт 5 чекліста запуску) або через `getChat`.

## Хто що має право робити

| | `bot/` (Python) | `worker/` (JS) |
|---|---|---|
| `sendMessage` у `DRAFTS_CHAT_ID` | ✅ так | ні |
| `copyMessage` у `CHANNEL_ID` | ❌ **ніколи** | ✅ тільки тут |
| `editMessageReplyMarkup` | ні | ✅ |
| `answerCallbackQuery` | ні | ✅ обов'язково |
| `deleteMessage` | ❌ ніколи | ❌ ніколи |

Змінна `CHANNEL_ID` у Python-коді не використовується взагалі. Це інваріант, який
перевіряється грепом у `/test-run`.

## HTML-розмітка

`parse_mode=HTML`. Telegram підтримує рівно цей набір тегів:

```
<b> <strong>   <i> <em>   <u> <ins>   <s> <strike> <del>
<span class="tg-spoiler">   <tg-spoiler>
<a href="...">   <code>   <pre>   <pre><code class="language-py">
<blockquote>   <blockquote expandable>
```

Чого немає і що ламає повідомлення з `400 Bad Request: can't parse entities`:

- `<br>` — переносу рядка тегом немає, тільки справжній `\n`
- `<p>`, `<div>`, `<ul>`, `<li>`, `<h1>` — не існують; списки робляться символами
  `➤` / `▫️` і переносами рядків
- вкладені однакові теги
- незакриті теги

`&`, `<`, `>` у **тексті** мають бути екрановані як `&amp;`, `&lt;`, `&gt;`.
Модель повертає готовий HTML, тому перед відправкою його треба валідувати
(`publish.sanitize_html`), а не екранувати цілком — інакше розмітка помре.

## Ліміти

| Що | Ліміт | Наслідок для коду |
|---|---|---|
| Довжина `text` | 4096 UTF-16 code units | обрізати по межі тега, не по байтах |
| Довжина `caption` | 1024 | медіа не шлемо, але пам'ятаємо |
| Повідомлень у групу | ~20/хв | між чернетками пауза ≥ 3 с |
| Повідомлень усього | 30/с | недосяжно за нашого обсягу |
| `callback_data` | **64 байти** | тому id короткий: `p:a1b2c3d4` = 10 байт |
| `answerCallbackQuery.text` | 200 символів | |
| Вікно відповіді на callback | ~15 с | воркер має відповісти першим ділом |

На `429` Telegram віддає `parameters.retry_after` у секундах — поважати його,
а не свій бекоф.

## copyMessage

```
copyMessage(chat_id=CHANNEL_ID, from_chat_id=<чат чернеток>, message_id=<id чернетки>)
```

- Копіює текст **разом із entities**, тобто HTML-форматування зберігається.
  Повторно `parse_mode` передавати не треба.
- `reply_markup` **не копіюється**. Не передаємо його — і в каналі пост виходить
  чистий, без кнопок. Це те, що треба.
- Повертає `{"message_id": N}` — id **нового** повідомлення в каналі.
  Саме він іде в `log:<id>.channel_message_id` і далі в `state.published`,
  бо на нього посилаються блоки «Раніше:» майбутніх постів.
- Бот має бути адміном у каналі з правом «Публікація повідомлень», а в групі
  чернеток — адміном, інакше `editMessageReplyMarkup` поверне помилку.

## Посилання на попередні пости

Для приватного каналу лінк на пост має вигляд `https://t.me/c/<internal>/<message_id>`,
де `<internal>` — це `CHANNEL_ID` без префікса `-100`. Модель отримує `message_id`
у списку останніх постів і сама будує `earlier_ids`; збірка URL — робота воркера
та документа 01, не Python-коду.

## Помилки, які не мають валити прогін

`400 chat not found`, `403 bot was blocked`, `429` — логуються як warning,
айтем пропускається, прогін триває. Валить прогін тільки відсутність секретів
і недоступність Google Docs.
